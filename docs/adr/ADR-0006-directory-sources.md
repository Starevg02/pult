# ADR-0006 — Источники каталога: Entra ID, Google Workspace, несколько доменов

- **Статус:** принято.
- **Дата:** 2026-11-20.

## Контекст

Портал строится вокруг Active Directory: учётки сотрудников приходят синхронизацией по LDAP (`ad_accounts`),
вход — паролем через bind в домен, Kerberos или OpenID Connect. Есть запросы на:

1. вход и синхронизацию через **Microsoft Entra ID** и **Google Workspace** — для организаций без локального AD;
2. **несколько доменов леса** (D-100, D-101) с выбором домена при входе;
3. **смену пароля AD** в портале.

## Решение

**Смена пароля AD — сделано в 0.2.0.** Сотрудник меняет пароль в «Моём профиле». Портал входит в домен под
сотрудником со старым паролем и заменяет `unicodePwd` (удаление старого значения и добавление нового). Это та
же операция, что смена пароля на компьютере: служебной учётке права на сброс паролей не нужны, а длину,
сложность, историю и минимальный срок проверяет домен. Функция выключена по умолчанию и работает только по
LDAPS. Неверный старый пароль считается неудачной попыткой входа.

**Вход через Entra ID и Google — работает через OIDC, если учётки приходят из AD.** Провайдер OIDC (Entra ID,
Google, Keycloak, ADFS) подтверждает личность, а портал находит учётку по имени из выбранного утверждения
(`preferred_username`, `upn`, `email`) среди синхронизированных из AD. Это покрывает гибридные организации,
где Entra ID синхронизируется с локальным AD.

**Организации без локального AD — не поддерживаются в 0.2.0.** Для них нужен второй источник каталога: чтение
пользователей и групп через Microsoft Graph или Google Directory API вместо LDAP. Это не делается сейчас, потому
что:

- операции в AD (разблокировка, сброс пароля, группы, отключение, доступы) — основа портала. В Graph и
  Directory API у них другая модель прав (роли приложения, делегирование администратора) и другие
  ограничения. Половина функций для облачного каталога потребовала бы отдельной реализации;
- проверить такую установку без настоящего арендатора Entra ID или Google Workspace нельзя, а выпускать
  непроверенную синхронизацию учёток — значит рисковать доступами.

Путь, который архитектура оставляет открытым:

- учётки уже привязаны к источнику (`ad_accounts.domain_id` → `ad_domains`). Облачный источник добавляется как
  ещё один вид записи источника и свой модуль синхронизации, который пишет те же поля: идентификатор,
  логин, имя, почта, подразделение, должность, состояние, группы;
- вход для облачного источника — только OIDC: пароль через bind там невозможен;
- операции в каталоге для облачного источника выключаются, пока для них нет реализации. Интерфейс уже умеет
  скрывать недоступные действия по правам и модулям.

**Несколько доменов — отложено до установки, где это нужно.** Схема готова: у учёток, синхронизаций и
компьютеров есть `domain_id`, логин уникален в пределах домена. Сейчас портал работает с первым включённым
доменом. Для леса нужно: пул контроллеров на каждый домен, синхронизация по каждому, выбор домена при входе
(или по суффиксу UPN и NetBIOS-имени в логине), домен в карточке сотрудника и в фильтрах. Без настоящего леса
с доверием это нельзя проверить, поэтому реализация ждёт такой установки.

## Последствия

- Организация с локальным AD получает вход через Entra ID или Google уже сейчас (OIDC, раздел 3.15
  руководства).
- Организации без AD портал в 0.2.0 не подходит. Это указано в документации, а не скрыто.
- Новые таблицы и запросы продолжают учитывать `domain_id`, чтобы не закрыть путь к нескольким доменам.
