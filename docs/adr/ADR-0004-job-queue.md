# ADR-0004 — Очередь фоновых задач в PostgreSQL

- **Статус:** принято.
- **Дата:** 2026-11-03.

## Контекст

Портал отправляет письма, выполняет операции в AD, синхронизирует каталог, считает SLA, делает резервные
копии. Главное требование — **постановка задачи в той же транзакции, что и бизнес-данные**: заявка и
письмо о ней, операция в AD и запись в аудит. Отдельный брокер (Redis, RabbitMQ) усложнил бы установку.

## Решение

Своя таблица `jobs` в PostgreSQL с захватом через `FOR UPDATE SKIP LOCKED` (крейт `pult-jobs`):

- ключ идемпотентности — повторная постановка не создаёт дубль;
- аренда задачи: задачу упавшего обработчика подхватывает другой по истечении аренды; опоздавший
  обработчик не затирает результат перехватчика;
- повторы с нарастающей паузой, затем статус `failed`, видимый в админке;
- паника и превышение времени — обычная ошибка с повтором.

**Расписание (cron)** — поверх той же таблицы: ключ слота `cron:<вид>:<момент>`, поэтому при нескольких
копиях сервера задача ставится один раз. Пропущенные слоты не догоняются пачкой. Встроенная задача
`jobs.prune` удаляет выполненные задачи старше 7 дней и упавшие — старше 30.

## Почему не готовая библиотека

Готовые очереди ведут свою схему и миграции отдельно от миграций портала, а стабильность их API на момент
решения не была проверена временем. Нужные возможности укладываются в небольшой крейт с интеграционными
тестами (`crates/pult-jobs/tests/queue.rs`): дубль по ключу, откат транзакции, параллельные обработчики без
повторов, перехват по аренде.

## Пересмотр

Если появятся приоритеты, зависимости между задачами или тысячи задач в секунду — новый ADR с замерами.
