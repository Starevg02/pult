# Как устроен Pult

Документ описывает, что реализовано в Pult, как это работает и почему выбрано именно так. Он нужен тем, кто
разворачивает, эксплуатирует, отлаживает или дорабатывает проект. Установка — в [install.md](install.md),
настройка после установки — в [guide.md](guide.md), работа администратора — в [admin-guide.md](admin-guide.md)
и [directory.md](directory.md), модель безопасности — в [security.md](security.md).

Описание относится к версии 0.1.0. Имена настроек даны так, как они записаны в коде: переменные `PULT_*`
и ключи таблицы `settings`.

## 1. Общая картина

Pult — портал IT-поддержки для организаций на Active Directory (AD). Он объединяет заявки, справочник
сотрудников, операции с каталогом AD, удалённую поддержку ПК и звонки из справочника.

Один исполняемый файл `pult` содержит HTTP- и HTTPS-сервер, все модули, исполнитель фоновых задач и
веб-интерфейс: собранное приложение React встраивается в бинарник (`web/dist`, `rust-embed`). Данные хранятся
в PostgreSQL. Отдельных брокеров, кэшей и служб нет.

```
Браузер сотрудника или инженера
        │ HTTPS 443
        ▼
[обратный прокси, по желанию] ──HTTP──┐
                                      ▼
┌──────────────────────────────────────────────────────────┐
│ pult (один бинарник, служба systemd `pult`)              │
│  HTTP/HTTPS · API · встроенный веб-интерфейс             │
│  модули: core, people, phonebook, helpdesk, directory,   │
│          remote                                          │
│  фоновые задачи: очередь и расписания в PostgreSQL       │
└──┬──────────────┬───────────────┬─────────────────┬──────┘
   │ SQL          │ LDAPS 636 или │ SMTP            │ AMI, TCP 5038
   ▼              │ StartTLS 389  │ (STARTTLS / TLS)│ (по желанию)
PostgreSQL        ▼               ▼                 ▼
          контроллеры домена  почтовый сервер     АТС (Asterisk)
          (два и более)

Агент на ПК (служба PultAgent, LocalSystem)
   ──HTTPS 443──► pult: регистрация, отчёт о сеансах раз в минуту,
                  обновление по подписи. Входящих портов агент не открывает.

Helper на ПК инженера
   ──HTTPS 443──► pult: обмен одноразового токена, итог подключения
   ──SMB 445 / RPC──► ПК пользователя: теневое подключение `mstsc /shadow`
```

Что Pult намеренно не делает:

- не передаёт поток удалённого сеанса: теневое подключение идёт напрямую между ПК инженера и ПК пользователя
  средствами Windows;
- не заменяет центр сертификации AD CS и не выпускает сертификаты контроллеров;
- не меняет атрибуты пользователей в AD (кроме операций, перечисленных в разделе 6.6);
- не принимает почту: заявки создаются в портале, письма только отправляются;
- не предоставляет собственную аутентификацию сотрудников: пароли проверяет AD.

## 3. Модули: контракт и включение

### 3.1. Контракт

Модуль — это крейт, который реализует трейт `Module` из `pult-core`:

```rust
pub trait Module<S> {
    fn name(&self) -> &'static str;                 // короткое имя: helpdesk, people…
    fn routes(&self) -> OpenApiRouter<S>;           // маршруты с описанием OpenAPI
    fn permissions(&self) -> Vec<Permission>;       // разрешения, которые модуль проверяет
    fn jobs(&self) -> Vec<JobDefinition>;           // фоновые задачи и их расписания
}
```

Три точки входа в ядро — маршруты, разрешения и задачи. Сборка выполняется в `pult-server`:

- `api::modules()` объединяет маршруты всех модулей в один роутер;
- `api::permissions()` собирает разрешения всех модулей для матрицы ролей и первичной раздачи системным ролям;
- `jobs::registry()` регистрирует обработчики задач и расписания.

Модули обращаются друг к другу только через публичные функции своих крейтов, а не через чужие таблицы
(правило записано в описании крейта `pult-core`).

Разрешение описывается структурой `Permission` с полями `code` (`<модуль>.<объект>.<действие>`, например
`helpdesk.ticket.work`), описанием для экрана ролей и системными ролями по умолчанию. Суперадминистратор имеет
все разрешения независимо от матрицы. Системные роли: `employee` (есть у всех активных пользователей),
`engineer`, `phonebook_editor`, `auditor`, `superadmin`. Членство в группах AD роли не определяет: роли
назначаются в портале.

### 3.2. Модули и их разрешения

| Модуль | Крейт | Выключается | Основные разрешения |
|---|---|---|---|
| core | `pult-core` | нет | `core.settings.manage`, `core.roles.manage`, `core.audit.view`, `core.mail.manage` |
| people | `pult-people` | нет | `people.ad.manage`, `people.sites.manage`, `people.link.manage` |
| phonebook | `pult-phonebook` | да (`phonebook`) | `phonebook.edit`, `phonebook.admin` |
| helpdesk | `pult-helpdesk` | да (`helpdesk`) | `helpdesk.ticket.work`, `helpdesk.ticket.create_on_behalf`, `helpdesk.admin` |
| directory | `pult-directory` | да (`directory`) | `directory.account.view`, `directory.user.unlock`, `directory.user.enable`, `directory.user.reset_password`, `directory.group.add_member`, `directory.manage` |
| remote | `pult-remote` | да (`remote`) | `remote.device.view`, `remote.connect.view`, `remote.connect.control`, `remote.manage` |

Вход, сеансы, роли, аудит, очередь и пул контроллеров работают всегда. Их нельзя выключить.

### 3.3. Включение и выключение

Модули включаются и выключаются в мастере первого запуска и в «Настройки → Система → Модули». Это настройка
(`settings`, ключ `org`, структура `Modules`), а не флаг сборки. Сборочный флаг есть один — `demo`.

- Запрос к API выключенного модуля получает ответ 404, как будто маршрута нет. Проверка делается по префиксу
  пути в `org::gate` (таблица `PREFIXES` в `pult-core/src/org.rs`). Например, `/api/helpdesk` относится к
  модулю `helpdesk`, а `/api/phonebook/calls` — к телефонии.
- Настройки модулей кэшируются на 5 секунд, поэтому переключение действует почти сразу.
- Данные выключенного модуля остаются. Включение возвращает всё как было.
- Телефония работает только со справочником (`Modules::validate`).
- Фоновые задачи проверяют, включён ли модуль: выключенный helpdesk не закрывает заявки, не шлёт напоминаний и
  не создаёт регламентных заявок.
- Поиск сотрудников (`/api/phonebook/persons`, отделы, должности) не выключается, потому что им пользуются
  заявки.

## 4. Путь запроса

### 4.1. TLS

Встроенный HTTPS реализован на `rustls` с криптопровайдером `ring`. Поддерживаются TLS 1.2 и TLS 1.3, ALPN
`h2` и `http/1.1`. Модуль — `pult-server/src/tls.rs`.

Откуда берётся сертификат портала:

1. Файлы, если заданы `PULT_TLS_CERT` и `PULT_TLS_KEY` (или секция `[tls]` в `pult.toml`). Цепочка PEM, ключ PEM.
2. Сертификат, которым управляет сам портал, если включён `PULT_AUTO_TLS=1` и задан `PULT_DATA_DIR`. Файлы
   лежат в `<PULT_DATA_DIR>/tls/` (`cert.pem`, `key.pem`). Если их нет, при первом запуске создаётся
   самоподписанный сертификат на 825 дней. Его заменяют в админке (`PUT /api/admin/tls`, только
   суперадминистратор): новая пара проверяется, записывается и применяется без перезапуска.
3. Без HTTPS: если `PULT_AUTO_TLS=0` и файлов нет, сервер слушает обычный HTTP. Так работают сервер за
   обратным прокси и разработка.

Вторая пара для другого имени (`PULT_TLS_EXTRA_CERT`, `PULT_TLS_EXTRA_KEY`) выбирается по SNI. Имена DNS из
второго сертификата (с поддержкой `*.` на один уровень) получают вторую пару. Остальные клиенты, в том числе
без SNI и по IP, получают основную. Так внутреннее имя портала и внешнее имя с публичным сертификатом
работают на одном адресе. Пары задаются целиком: только сертификат или только ключ — ошибка при старте.

Заголовок `Strict-Transport-Security` (`max-age=31536000`) отдаётся только тогда, когда HTTPS обслуживает сам
Pult. За обратным прокси этот заголовок задаёт прокси.

Установка сертификата и настройки пакета описаны в [install.md](install.md), раздел 6.

### 4.2. Заголовки ответа и сроки запроса

Каждый ответ содержит (`pult-server/src/http.rs`):

- `X-Content-Type-Options: nosniff`;
- `Referrer-Policy: no-referrer`;
- `Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`;
- `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`;
- `Cross-Origin-Opener-Policy: same-origin`.

Ответы `/api/` получают `Cache-Control: no-store`, если обработчик не задал свой заголовок (логотип организации
кэшируется). Так ФИО, телефоны и список сеансов не остаются в кэше браузера на общем компьютере.

Сроки:

- на чтение заголовков запроса — 10 секунд (медленные соединения закрываются);
- на весь запрос, включая тело, — 60 секунд;
- для загрузки вложения или пакета агента больше 2 МБ — 600 секунд; эти маршруты читают тело только после
  проверки входа и прав.

Ответ `408` с кодом `request_timeout` отдаётся, если запрос не уложился в срок. Поток событий (SSE) срок не
ограничивает: ответ уже отдан.

### 4.3. Доверенные прокси и адрес клиента

Адрес клиента нужен для лимитов входа, аудита и проверки «сети организации». За обратным прокси соединение
приходит от прокси, поэтому адрес клиента берётся из `X-Forwarded-For`, но только от доверенных адресов.

- `PULT_TRUSTED_PROXIES` — адреса или сети (CIDR) прокси через запятую.
- Заголовок `X-Forwarded-For` разбирается справа налево. Первый адрес, который не принадлежит доверенному
  прокси, и есть адрес клиента. Левая часть заголовка пришла от клиента, ей не верят.
- Запрос через прокси, которому не доверяют, помечается как «непроверенный адрес». Для входа такой запрос
  считается внешним, то есть из интернета. Иначе прокси на этом же сервере открыл бы вход без второго фактора
  всем.
- Метрики `/metrics` отдаются только прямому запросу с адреса `127.0.0.1` или `::1` без заголовков прокси, либо
  с токеном `Authorization: Bearer` из `PULT_METRICS_TOKEN`. Запрос через nginx на том же сервере без доверенного
  прокси не считается «своим».
- Если запросы идут через прокси на этом же сервере, а `PULT_TRUSTED_PROXIES` не задан, в журнале появляется
  предупреждение.

### 4.4. Сеансы и cookie

Сеанс — случайный токен 32 байта (256 бит) в base64url.

- Cookie: `__Host-pult_session`, с флагами `HttpOnly; Secure; SameSite=Lax; Path=/`. Имя с префиксом `__Host-`
  браузер принимает только для своего хоста без `Domain`. Без HTTPS (только разработка, `PULT_INSECURE_COOKIES=1`)
  cookie называется `pult_session` и без `Secure`.
- В базе хранится только SHA-256 от токена (таблица `sessions`, колонка `id`). Украденная копия таблицы не даёт
  рабочих cookie.
- Срок: бездействие 8 часов по умолчанию (1–72, `session_idle_hours`), абсолютный срок 7 дней по умолчанию
  (1–30, `session_absolute_days`). Продление бездействия пишется в базу не чаще раза в минуту.
- Сеанс закрывается при выходе и при отключении учётки в AD (синхронизация закрывает все сеансы пользователя).
  Сеанс не действует, если учётка отключена или пропала из AD: это проверяется в каждом запросе. Задача
  `sessions.prune` удаляет истёкшие сеансы каждый час.
- Вход возвращает `Cache-Control: no-store`.
- Если связь с доменом потеряна и политика `ad_outage_policy` равна `block` (по умолчанию), после трёх
  неудачных проверок подряд сеансы приостанавливаются (ответ `503`, код `ad_unavailable`). При `grace` работа
  продолжается ограниченное время (`ad_outage_grace_minutes`, по умолчанию 30).

Токен API — это другой способ входа. Он передаётся заголовком `Authorization: Bearer pult_…`, токен
ограничен чтением: любой запрос, кроме `GET`, `HEAD` и `OPTIONS`, отклоняется с `403`. Разрешения токена —
пересечение выданных ему и тех, что есть у владельца.

### 4.5. CSRF

Изменяющие запросы (все методы, кроме `GET`, `HEAD`, `OPTIONS`) проверяются в извлечении `CurrentUser`
(`pult-core/src/session.rs`). Обработчик, который требует пользователя, защищён сам: отдельно включать проверку
не нужно.

- При входе создаётся CSRF-токен (32 байта). Он хранится в строке сеанса (`sessions.csrf_token`) и выдаётся в
  cookie `__Host-pult_csrf`, которую читает скрипт интерфейса (`web/src/api/client.ts`).
- Клиент копирует значение в заголовок `X-CSRF-Token`. Сервер сравнивает заголовок со значением из строки сеанса
  за постоянное время. Отсутствие заголовка или несовпадение — ошибка `403` с кодом `csrf`.
- Вход принимает только JSON. Форма с другого сайта не отправит `application/json`, поэтому CSRF-атака на вход
  не проходит.

### 4.6. Права

Права проверяются в каждом обработчике: `user.require(&perm::X)` или `user.require_superadmin()`. Общего слоя,
который бы проверял права по пути, нет. Список разрешений модуля — в его крейте (например,
`pult-helpdesk/src/lib.rs`, блок `perm`).

Проверка делается на сервере при каждом запросе. Интерфейс прячет недоступные разделы, но это только удобство.
Права пользователя загружаются по его ролям на каждый запрос (`rbac::load_grants`).

### 4.7. Журнал аудита

Журнал (таблица `audit_log`) пишется через `audit::record`. Если запись делается в той же транзакции, что и
изменение, она появляется в журнале только вместе с ним.

Целостность обеспечивает сама база (миграция `20261106000000_core.sql`):

- триггер `audit_log_chain` перед вставкой берёт advisory-блокировку `7231001`, присваивает номер и вычисляет
  `hash = SHA-256(prev_hash || содержимое)`. Вставки идут по одной, поэтому порядок номеров совпадает с порядком
  цепочки;
- триггеры `audit_log_no_update` и `audit_log_no_truncate` запрещают `UPDATE`, `DELETE` и `TRUNCATE`;
- функция `audit_verify()` проходит всю цепочку. Задача `audit.verify` запускается ежедневно в 02:40, результат
  сохраняется в настройках (`audit_verify`) и видно в админке.

Журнал не очищается: сроки хранения его не касаются (`pult-core/src/retention.rs`).

Ограничение: тот, кто владеет таблицами (роль приложения или суперпользователь), может отключить триггеры.
Цепочка выявит подмену, только если последний хэш сохранён вне базы. Об этом подробнее в
[security.md](security.md).

Пароли, токены и временные пароли в журнал не попадают. В `details` записывается «было/стало» только для
изменённых полей (`audit::diff`).

### 4.8. Лимиты

| Что ограничивается | Значение по умолчанию | Где задаётся |
|---|---|---|
| Неудачные входы на один логин за окно | 5 | `login_max_failures_per_login`, Настройки → Безопасность |
| Неудачные входы с одного IP за окно | 20 | `login_max_failures_per_ip` |
| Окно для двух предыдущих лимитов | 5 минут | `login_window_minutes` (1–60) |
| Неудачные входы из интернета на один логин за сутки | 20, потом вход из интернета закрыт до следующих суток | в коде (`EXTERNAL_FAILURES_PER_DAY`) |
| Одновременные проверки внешнего входа на один логин | 1, остальным ответ 429 | в коде |
| Неверные коды второго фактора при подключении и отключении | 5 за 5 минут, потом пауза 5 минут | в коде |
| Одновременные проверки Kerberos (`/api/auth/negotiate`) | 4, остальным 429 | в коде |
| Одновременные загрузки файлов на сервер | 8 | в коде |
| Одновременные загрузки одного пользователя | 2 | в коде |
| Неприкреплённые файлы пользователя за сутки | 50 файлов или 500 МБ | в коде |
| Размер вложения | 25 МБ | `max_file_mb` в настройках Helpdesk (1–100) |
| Размер тела обычного запроса | 2 МБ (предел axum по умолчанию) | в коде |
| Публичная форма «Не могу войти» | 3 обращения в час с адреса; только из заданных подсетей | настройки Helpdesk |
| Срок одноразовой ссылки подключения | 60 секунд; итог принимается 10 минут | в коде (`connect.rs`) |
| Отчёт агента | раз в 60 секунд; сервер допускает 30–600 | `report_interval_secs` в настройках удалённой поддержки |

Лимит по логину и по IP считает неудачи из таблицы `login_attempts`. Попытки, которые отклонил сам лимит
(`throttled`), не учитываются. Записи старше 30 дней удаляет `sessions.prune`.

## 5. Вход

### 5.1. Вход паролем AD

Вход — это проверка логина и пароля контроллером домена через LDAP bind. Пароль Pult не хранит и не сравнивает
сам. Код входа — `pult-people/src/auth.rs` (`login`), подключение — `pult-ad/src/pool.rs` (`authenticate`).

Шаги:

1. Логин приводится к ключу. `CORP\ivanov`, `ivanov@corp.example.test` и `IVANOV` дают один ключ `ivanov`.
   Если логин выглядит как UPN, он сопоставляется с `sAMAccountName` по зеркалу `ad_accounts`. Начало UPN не
   обязано совпадать с логином.
2. Проверяются лимиты (раздел 4.8). Внешние запросы сериализуются по логину.
3. Для внешнего входа, если пользователю нужен код (он подключил его сам или его роль в
   `totp_required_roles`), код проверяется до обращения к AD (раздел 5.3).
4. Служебная учётка ищет DN пользователя по `sAMAccountName` или `userPrincipalName`. Значение экранируется
   функцией `ldap_escape`. Пустой пароль отклоняется до сетевого запроса: без этого анонимный bind прошёл бы
   как успешный.
5. Пользователь делает bind своим DN и паролем на том же контроллере. Неверный пароль на другом контроллере не
   повторяется: это не удваивает счётчик блокировки в домене.
6. Учётка сопоставляется с зеркалом по `objectGUID`. Если зеркала ещё нет, выполняется точечная синхронизация
   по DN. Отключённая учётка получает отказ.
7. Пользователь заводится или обновляется (`users`), при необходимости выдаётся первый суперадминистратор
   (раздел 5.5). Пишутся аудит `auth.login` и сеанс.

Ответ при неудаче содержит код причины, который переводится на язык запроса:

| Код | Причина |
|---|---|
| `invalid_credentials` | неверный логин или пароль; нет такой учётки — тот же ответ |
| `password_expired` | пароль истёк или нужна смена |
| `account_disabled` | учётка отключена |
| `account_locked` | учётка заблокирована в домене |
| `account_expired` | срок учётки истёк |
| `logon_hours`, `workstation` | вход запрещён по часам или по компьютеру |

Pult различает эти состояния так же, как вход в Windows. Это раскрывает состояние учётки тому, кто знает логин.
Принятый компромисс описан в [security.md](security.md).

### 5.2. Контроллеры домена и переключение

Подключение — только по LDAPS (порт 636 по умолчанию) или StartTLS (порт 389). Схему `ldap://` в адресе
контроллера нельзя указать: режим задаётся параметром `tls`. Проверка сертификата обязательна, отключить её
нельзя. Доверенные корни — системное хранилище и CA домена (`ca_cert` или `ca_cert_pem`).

Контроллеры перебираются по порядку, начиная с того, который последним ответил. При сетевой ошибке, ошибке TLS
или таймауте (`timeout_secs`, 5 секунд) берётся следующий. Ответ самого контроллера (например, неверный пароль)
перебор не продолжает. Если не ответил ни один контроллер, возвращается `ad_unavailable` с причиной по каждому.

Запомненный контроллер хранится в памяти процесса. Возврата к первому контроллеру по таймеру в коде нет:
после перезапуска перебор начинается с первого в списке.

### 5.3. Второй фактор (код из приложения)

Второй фактор — TOTP по RFC 6238 (HMAC-SHA1, 6 цифр, шаг 30 секунд, допуск ±1 шаг). Код совместим с обычными
приложениями-аутентификаторами. QR-кода нет: ключ вводится вручную или ссылкой `otpauth://`.

- Код нужен только при входе из-за пределов сетей организации (настройка `internal_networks`, по умолчанию
  `10/8`, `172.16/12`, `192.168/16`, `fc00::/7`). Изнутри сети вход паролем без кода.
- Код нужен тем, кто подключил его в профиле. Кроме того, код обязателен для ролей из списка
  `totp_required_roles` (по умолчанию пусто).
- Код проверяется до AD. Тот, кто подключил код, при подборе пароля из интернета не обращает домен к учётке.
- Один код — один вход: шаг занимается атомарно (`totp_last_step`), повтор перехваченного кода не проходит.
- Секрет хранится зашифрованным (раздел 8.4). Подключение и отключение кода — только из сети организации и
  только из браузера. Сброс делает суперадминистратор, все сеансы пользователя закрываются.
- Учётка без кода проверяется по времени так же, как с ним: заглушечный секрет тратит то же время.
- Ответ `otp_required` говорит, что логину нужен код, подключённый или по роли. Это принятый компромисс:
  логин как таковой проверяется, а пароль — только после кода. Неверный код дает `invalid_otp`.

Для внешнего входа отдельно считаются неудачи (`login_attempts.external`). Перебор из интернета не закрывает
вход сотрудникам в офисе.

### 5.4. Вход через Kerberos (SPNEGO): что реализовано

Маршрут `GET /api/auth/negotiate` принимает заголовок `Authorization: Negotiate` и проверяет билет Kerberos
ключом из keytab (`KRB5_KTNAME`) через MIT GSSAPI (`libgssapi`). Своего разбора Kerberos в коде нет. Принимается
только Kerberos: NTLM отклоняется. GSSAPI входит только в сборку под Linux, на Windows маршрут отвечает `501`.
Файл `pult-server/src/negotiate.rs`.

Сейчас маршрут только распознаёт пользователя и возвращает его принципал (например,
`ivanov@CORP.EXAMPLE.TEST`). Сеанс по результату не создаётся. Единственный вызов маршрута в интерфейсе —
страница «Состояние». Вход в портал без пароля не реализован: сотрудник входит паролем AD.

### 5.5. Первый суперадминистратор

Первый суперадминистратор назначается мастером первого запуска: вошедший паролем AD при завершении мастера
получает роль. Для установки из конфигурации задаётся `PULT_INITIAL_SUPERADMIN=DOMAIN\логин`. Роль выдаётся при
входе этого логина, только пока суперадминистраторов нет (проверка под advisory-блокировкой `7231003`).

## 6. Синхронизация с AD

### 6.1. Учётки чтения и записи

Pult работает с каталогом двумя учётками. Обе создаёт администратор домена.

- Служебная учётка чтения (`bind_dn`, в мастере — поле «Служебная учётка»). Обычный пользователь домена без
  особых прав. Ею выполняются синхронизация, проверка связи, поиск DN при входе.
- Учётка записи (раздел 6.6) — отдельная, с делегированными правами только на нужные OU и группы. Не входит в
  привилегированные группы.

Пароли обеих учёток хранятся в базе зашифрованными (раздел 8.4). В ответах API их нет.

### 6.2. Полная и инкрементальная синхронизация

Код — `pult-ad/src/sync.rs` и `pult-people/src/sync.rs`.

- Полная синхронизация читает все учётки по фильтру `user_filter` (по умолчанию `objectCategory=person` и
  `objectClass=user`) постранично, по 500 записей. Запускается ежедневно в 03:00 и вручную.
- Инкрементальная синхронизация читает учётки с `uSNChanged` больше сохранённого значения. Запускается каждые
  5 минут.
- `uSNChanged` есть у каждого контроллера свой. Поэтому USN сохраняется вместе с именем контроллера. Если
  выборка пошла с другого контроллера, синхронизация переходит на полную.
- Значение `highestCommittedUSN` читается до выборки. Изменения, сделанные во время прохода, попадут в
  следующую инкрементальную синхронизацию.
- Одна синхронизация домена за раз: блокировка `pg_try_advisory_xact_lock(7231020)` действует на транзакцию,
  поэтому оборванная задача не оставляет блокировку на соединении.

Задача `ad.health` проверяет связь каждую минуту. Задача `ad.computers` читает компьютеры домена каждые
15 минут: по ним подставляются ПК в заявках и проверяется регистрация агентов.

### 6.3. Связь учёток с сотрудниками

Справочник и учётки AD — разные сущности. В справочнике есть сотрудники без учётки AD (например, без своего
компьютера), учётка может существовать без записи в справочнике.

При синхронизации учётка связывается с сотрудником по правилам из `pult-people/src/sync.rs` (`link_account`):

1. Если совпал адрес электронной почты и он однозначен, связь делается сразу.
2. Если логин почты совпадает с логином AD и фамилия похожа, связь ставится в очередь подтверждения
   администратором (`person_link_candidates`), администратору приходит уведомление.
3. Иначе, если настройка `people_link.auto_create_persons` включена (по умолчанию да), создаётся новый
   сотрудник. Служебные учётки без имени и фамилии в справочник не попадают.

Атрибуты, пришедшие из AD, в портале не редактируются. Для сотрудника хранятся источники полей
(`person_field_sources`).

### 6.4. Отключённые и пересозданные учётки

- Учётка стала отключённой или пропала из выборки полной синхронизации: пользователь становится неактивным,
  его сеансы закрываются, сотрудник архивируется с причиной `ad_disabled`. Включение в AD возвращает всё как
  было.
- Учётка, которую удалили и создали заново с тем же логином (новый `objectGUID`), не наследует роли, сеансы и
  карточку прежней. Старая запись переименовывается с суффиксом `~<часть GUID>`, закрывается и получает запись
  в аудите `ad.account.replaced`. Логин мог достаться другому человеку.

### 6.5. Защита от массового отключения

Если проход отключил бы больше 20 учёток и больше пятой части активных либо все активные учётки, синхронизация
ничего не меняет. Она завершается ошибкой `ad_sync_mass_disable` и уведомлением суперадминистраторам. Причина
обычно одна: пустая или урезанная выборка из-за сломанного фильтра, базового DN или прав служебной учётки.
Администратор может подтвердить отключение вручную в админке.

### 6.6. Операции записи в AD

Изменения каталога выполняются только пятью типизированными операциями: добавить в группу, разблокировать,
включить, отключить, сбросить пароль. Произвольного LDAP modify нет. Крейт `pult-directory`, подробности
записи — в [directory.md](directory.md).

Важные свойства кода:

- право и область проверяются при запросе и ещё раз при выполнении (`ops::authorize`). Отозванное право или
  выведенный из области объект дают ошибку, AD не меняется;
- учётка с `adminCount = 1` (защищённая AdminSDHolder) не меняется ни одной операцией (`pult-ad/src/write.rs`,
  поле `protected`);
- сброс пароля выполняется только по LDAPS (`write.rs`, проверка `tls != Ldaps`);
- временный пароль — 16 символов, все четыре класса, из системного генератора. Его показывают запросившему один
  раз, неполученный стирается через сутки (задача `sessions.prune`);
- операция над собственной учёткой запрещена (`own_allowed`). Исключение — запрос доступа, который согласовал
  владелец ресурса;
- после записи задача читает объект заново и сверяет результат, а «было/стало» пишется в аудит.

## 7. Фоновые задачи

### 7.1. Очередь

Очередь — таблица `jobs` в PostgreSQL (`pult-jobs`, миграция `20261103000001_jobs.sql`). Брокера нет. Решение
описано в [ADR-0004](adr/ADR-0004-job-queue.md).

- Постановка — обычный `INSERT` в той же транзакции, что и бизнес-данные. Задача из откатанной транзакции не
  появляется. Пример: заявка и письмо о ней, либо операция AD и запись в аудит.
- Ключ идемпотентности (`idempotency_key`, уникальный) не даёт поставить дубль. Для операций каталога ключ
  привязан к намерению пользователя.
- Захват: `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)`. Несколько обработчиков и несколько копий
  сервера не берут одну задачу дважды.
- Аренда: `locked_until` — 300 секунд. Обработчику дано 240 секунд (`job_timeout`). Если обработчик умер,
  задачу подхватит другой по истечении аренды.
- Итог записывается только если задача всё ещё за этой попыткой (`attempts = …`). Опоздавший обработчик не
  затирает результат перехватчика.
- Ошибка, паника и превышение времени — обычная ошибка с повтором. Пауза: 30 секунд · 2^(n−1), не больше
  часа. После `max_attempts` (по умолчанию 5) задача получает статус `failed` и видна в админке.
- Исполнитель: до 4 задач одновременно (`[jobs] concurrency`), опрос раз в 2 секунды, при остановке дожидается
  задач до 20 секунд.
- Копия сервера без задач: `[jobs] enabled = false`.

### 7.2. Расписания

Расписания — это cron-выражения. Время читается в смещении `[jobs] utc_offset` (по умолчанию `+03:00`), потому
что в России нет перехода на летнее время.

Слот расписания имеет ключ `cron:<вид>:<момент>`. Несколько копий сервера ставят слот один раз. Пропущенные
слоты не догоняются пачкой: в окне 1 час ставится только последний. Задача `jobs.prune` удаляет выполненные
задачи старше 7 дней и упавшие старше 30.

| Задача | Расписание | Где объявлена |
|---|---|---|
| `ad.sync.incremental` | `*/5 * * * *` | people |
| `ad.sync.full` | `0 3 * * *` | people |
| `ad.health` | `* * * * *` | people |
| `ad.computers` | `*/15 * * * *` | people |
| `mail.send` | `* * * * *` | core |
| `sessions.prune` | `7 * * * *` | core |
| `audit.verify` | `40 2 * * *` | core |
| `system.backup` | `30 2 * * *` | core |
| `jobs.prune` | `17 3 * * *` | core |
| `helpdesk.auto_close` | `*/10 * * * *` | helpdesk |
| `helpdesk.sla` | `* * * * *` | helpdesk |
| `helpdesk.orphans` | `* * * * *` | helpdesk |
| `helpdesk.recurring` | `* * * * *` | helpdesk |
| `helpdesk.waiting` | `17 * * * *` | helpdesk |
| `helpdesk.weekly_report` | `0 8 * * 1` | helpdesk |
| `helpdesk.files_gc` | `23 4 * * *` | helpdesk |
| `helpdesk.webhook` | по событию | helpdesk |
| `directory.operation` | по событию | directory |

Список взят из `pult-server/src/jobs.rs` и `pult-helpdesk/src/jobs.rs`. Задачи модуля `helpdesk` ничего не делают,
пока модуль выключен (раздел 3.3).

Почта: письма ставятся в `outbox_emails`, задача `mail.send` отправляет очередь раз в минуту, не дольше 150 секунд
за запуск. Остаток уходит в следующий запуск. Отправка идёт по STARTTLS или по TLS, с проверкой сертификата
сервера. Без шифрования отправка возможна только при `PULT_INSECURE_MAIL=1` (разработка).

## 8. Данные

### 8.1. PostgreSQL

Pult требует PostgreSQL 15 или новее. Расширения `pg_trgm` и `unaccent` создаёт администратор PostgreSQL:
пакет делает это от имени `postgres`, роли `pult` суперпользовательские права не нужны. Подключение задаётся `PULT_DATABASE_URL` или
`PULT_DATABASE_PASSWORD_FILE` (пароль из файла).

Схема состоит из таких областей:

| Область | Таблицы (примеры) |
|---|---|
| Настройки и очередь | `settings`, `jobs` |

### 8.2. Миграции

Миграции лежат в `migrations/` и встраиваются в бинарник (`sqlx::migrate!`). Правила:

- только вперёд: новый файл с новой меткой времени, а не правка применённого (правило проекта в
  [CONTRIBUTING.md](../CONTRIBUTING.md));
- `pult migrate` применяет все недостающие миграции одной транзакцией PostgreSQL под advisory-блокировкой
  (`pult-server/src/migrate.rs`). Сбой в любой миграции откатывает всё обновление. Таблица `_sqlx_migrations`
  та же, что у `sqlx`;
- мигратор отказывается работать, если в базе есть миграция, которой нет в бинарнике (база от более новой
  версии), если уже применённый файл изменён (другая контрольная сумма), если миграция отмечена как неудачная,
  и если миграция требует выполнения вне транзакции;
- служба выполняет `pult migrate` перед каждым запуском (`ExecStartPre` в `deploy/systemd/pult.service`), в
  образе Docker — командой `CMD`. Уже применённые миграции пропускаются.

### 8.3. Вложения

Файлы заявок хранятся на диске в `<PULT_DATA_DIR>/files/<первые 2 hex SHA-256>/<SHA-256>` (`pult-helpdesk/src/files.rs`).
В таблице `files` — хэш, размер, MIME-тип, исходное имя и автор.

- Разрешён список расширений (`files.rs`, константа `ALLOWED`). Для двоичных форматов проверяется сигнатура
  первых байт, текстовые файлы проверяются на нулевые байты.
- Размер ограничен настройкой `max_file_mb` (по умолчанию 25 МБ).
- Скачивание: картинки PNG, JPEG, GIF и WebP открываются в ленте (`Content-Disposition: inline`), остальное —
  только скачивание (`attachment`). Ответ содержит `Cache-Control: no-store`.
- Неприкреплённые файлы хранятся сутки, затем удаляются задачей `helpdesk.files_gc` (в 04:23).
- Каталог вложений — локальный каталог сервера. Общего хранилища для нескольких копий в коде нет.

### 8.4. Ключ шифрования и секреты

`secret.key` — ключ, из которого выводится ключ шифрования секретов в базе.

- Ключ задаётся переменной `PULT_SECRET_KEY` (не короче 32 символов, без `CHANGEME`; короче — сервер не
  стартует) или создаётся сам в `<PULT_DATA_DIR>/secret.key` при первом запуске. Файл создаётся с правами `0600`
  и не перезаписывается.
- Из ключа HKDF-SHA256 (соль `pult`, контекст `pult/db-secrets/v1`) выводится 256-битный ключ AES-256-GCM.
- Формат шифротекста: байт версии `1`, nonce 12 байт, данные с меткой аутентичности. Байт версии участвует в
  аутентификации как associated data.
- Зашифрованы: пароль служебной учётки чтения, пароль учётки записи, пароль SMTP, секреты вебхуков, секрет
  второго фактора каждого пользователя, токен интеграции телефонии.

Потерянный ключ делает секреты нечитаемыми. Сменить ключ без перешифровки нельзя. Восстановление после потери
описано в [install.md](install.md), раздел 8.

Пароли в журнале не появляются: тип `Secret` печатает заглушку в `Debug` и `Display`, не сериализуется и
затирается при освобождении памяти (`pult-core/src/secret.rs`).

### 8.5. Резервные копии

Задача `system.backup` делает копию каждую ночь в 02:30, пакет делает копию перед каждым обновлением, команда
`pult backup` — по требованию (`pult-server/src/backup.rs`).

Копия — каталог `pult-ГГГГММДД-ЧЧММСС` в `PULT_BACKUP_DIR` (по умолчанию `<PULT_DATA_DIR>/backups`, права `0700`).
Внутри:

- `db.dump` — дамп базы `pg_dump` в формате custom. Пароль передаётся переменной `PGPASSWORD`, а не аргументом;
- `files/` — вложения;
- `tls/` — каталог сертификата портала, управляемого Pult. Копируется целиком.

Незавершённая копия создаётся во временном каталоге `.partial`, затем переименовывается. Хранятся последние 14
копий. Результат последней копии виден в админке (настройка `backup_status`). При ошибке суперадминистраторы
получают уведомление.

Ключ шифрования `secret.key` в копию не входит. Копия без ключа не раскрывает пароли служебных учёток.

### 8.6. Пакет .deb: установка, обновление, откат

Пакет собирается скриптом `deploy/deb/build.sh`, его файлы — в `deploy/deb/debian/`. Что делают скрипты:

- `preinst` (install и upgrade): сохраняет прежний бинарник в `/var/lib/pult-rollback/pult.prev` (каталог только
  для root), записывает метку обновления и останавливает службу;
- `postinst` при установке: создаёт пользователя `pult`, каталоги, пишет `/etc/pult/pult.env` (`root:pult 0640`).
  Если PostgreSQL на сервере есть, создаёт роль и базу `pult` со случайным паролем, пароль передаётся через stdin.
  Затем применяет миграции и запускает службу. Служба слушает `0.0.0.0:443`, включён `PULT_AUTO_TLS=1`;
- `postinst` при обновлении: резервная копия, миграции, перезапуск и проверка, что служба активна. Если
  резервная копия или миграция не удалась до применения изменений, база не меняется, прежний бинарник
  возвращается и служба запускается на нём. Если служба не поднялась уже после миграций, автоматического возврата
  нет: прежняя версия с обновлённой базой не стартует. Тогда база восстанавливается из резервной копии;
- `prerm` и `postrm`: при удалении останавливают службу и отключают её. Данные (база, `/etc/pult`,
  `/var/lib/pult`, ключ и копии) не удаляются даже при `purge`.

Подробные шаги установки, обновления и восстановления — в [install.md](install.md), разделы 4, 8, 9 и 10.

Служба (`deploy/systemd/pult.service`) работает под пользователем `pult`, с `NoNewPrivileges`, `ProtectSystem=strict`,
записью только в `/var/lib/pult`, фильтром системных вызовов `@system-service`, `MemoryDenyWriteExecute`,
адресами только `AF_INET`, `AF_INET6` и `AF_UNIX`. Единственная capability — `CAP_NET_BIND_SERVICE` для порта 443.

### 8.7. Docker

`deploy/compose.yml` поднимает три сервиса: одноразовый контейнер, который создаёт пароль базы в томе `secrets`;
PostgreSQL 17; сам Pult из `deploy/Dockerfile` (сборка web и Rust, затем образ `debian:bookworm-slim`). Внутри
контейнера сервер слушает `8443`, снаружи порт задаётся `PULT_HTTPS_PORT` (по умолчанию 443). Том `data` содержит
`secret.key`, вложения и сертификат. Резервная копия — тома `pult_pgdata` и `pult_data`.

## 9. Удалённая поддержка

Pult не содержит собственного протокола удалённого доступа. Портал решает, можно ли подключиться и как
(с согласием пользователя или без него). Сам сеанс делает Windows (`mstsc /shadow`).

### 9.1. Агент

Агент — служба `PultAgent` под LocalSystem, которую ставит MSI (`deploy/windows/agent.wxs`).

1. Регистрация. Агент отправляет `POST /api/agent/v1/enroll` с токеном регистрации `pae_…`. Сервер проверяет:
   токен не отозван и не истёк; компьютер с таким именем есть среди включённых компьютеров AD; если
   `require_dns_match` включён (по умолчанию да), адрес запроса совпадает с адресом компьютера в DNS (записи
   `ad_computers`). Затем выдаётся ключ агента `pak_…`. Сервер хранит только его SHA-256, ключ показывается
   один раз.
2. Отключённый администратором компьютер сам не возвращается: повторная регистрация отклоняется (`device_deactivated`).
3. Отчёт. Агент отправляет `POST /api/agent/v1/report` с ключом в `Authorization: Bearer`: имя компьютера, домен,
   версию ОС и агента, адреса и сессии (`WTSEnumerateSessions`). Частота — раз в минуту, плюс при входе, выходе и
   блокировке. Сервер подсказывает паузу (30–600 секунд). ПК считается «в сети», если отчёт был не позже
   `online_minutes` назад (по умолчанию 3 минуты).
4. Агент работает только с исходящими соединениями HTTPS. Сертификат портала проверяется по хранилищу Windows.

Параметры агента читаются из `HKLM\SOFTWARE\Pult\Agent` или из политики `HKLM\SOFTWARE\Policies\Pult\Agent`.
Подробно — в [admin-guide.md](admin-guide.md), раздел 3.

### 9.2. Обновление агента

Обновление подписывается Ed25519 закрытым ключом, который хранится у администратора офлайн. Сервер подписывать
не может. Агент знает открытый ключ (задан при установке, `UPDATEKEY`).

Подписывается сообщение `pult-agent-update\nwindows-x86_64\n<версия>\n<SHA-256>\n` (`pult-api-types`,
`update_message`). Агент проверяет SHA-256 и подпись, принимает только версию новее установленной и не
откатывается на старую сборку. Команда на обновление приходит в ответе на следующий отчёт агента.

### 9.3. Подключение инженера

1. Инженер нажимает «Подключиться» в карточке заявки или ПК. Вызывается `POST /api/remote/connections`.
2. Сервер проверяет право (`remote.connect.view` или `remote.connect.control`), политику ПК (`policy.rs`: правила
   «Подключение запрещено», «Только с согласием», шаблоны имён со `*`), наличие сессии у заявителя или выбранной
   сессии. Каждое подключение и каждый отказ пишутся в аудит.
3. Создаётся запись подключения и одноразовый токен `pc_…` на 60 секунд. Ссылка `pult://connect?t=…` открывается
   в браузере, и браузер передаёт её helper.
4. Helper на ПК инженера: проверяет ссылку, обменивает токен (`POST /api/remote/v1/exchange`; токен принимается
   один раз и только в течение 60 секунд), получает имя ПК, номер сессии, режим и признак согласия. Имя ПК
   проверяется как имя хоста. Адрес портала берётся только из его настройки в `HKCU`, не из ссылки.
5. Helper запускает `mstsc /v:<ПК> /shadow:<сессия> [/control] [/noConsentPrompt | /prompt]` списком аргументов,
   без командной оболочки. Путь к `mstsc` строится от `%SystemRoot%`, а не по имени из `PATH`.
6. Helper сообщает итог (`POST /api/remote/v1/result`) тем же токеном в течение 10 минут. Итог попадает в заметку
   заявки и в журнал. Итог сообщает сам helper, поэтому он не подтверждает, что пользователь принял запрос.

Токены регистрации, ключи агентов и токены подключения хранятся как SHA-256. Токен подключения живёт минуту, ключ
агента действует до отзыва устройства.

Быстрые действия (диск `C$`, управление компьютером, PowerShell) требуют `remote.connect.control`. На ПК с
правилом «Только с согласием» они запрещены, потому что дают доступ без ведома пользователя.

## 10. Язык интерфейса и ответов

Поддерживаются русский, английский и китайский. Русский — исходный язык (подробности — в
[localization.md](localization.md)).

- Интерфейс: строки берутся по ключам `t("…")` из `web/src/i18n/ru.json`, `en.json` и `zh.json`. Линтер не
  пропускает русский текст прямо в разметке.
- Сервер: язык запроса выбирает middleware `pult_core::l10n::scope`. Порядок: cookie `pult_lang`, заголовок
  `Accept-Language`, русский. Переводятся сообщения об ошибках, описания прав, подписи отчётов и выгрузки.
- Каталоги переводов сервера: `crates/pult-core/src/l10n/en.tsv` и `zh.tsv`, формат `русский<TAB>перевод`.
  Тест `crates/pult-core/tests/l10n_coverage.rs` падает, если русская строка не переведена или в каталоге
  осталась лишняя запись.
- Письма отправляются на языке получателя (`users.locale`). Фоновые задачи язык запроса не знают. Язык установки
  задаётся в админке и применяется к новым учётным записям.
- Данные, введённые людьми (названия категорий, статьи, комментарии), не переводятся.

## 14. Состояние в памяти процесса

Часть состояния живёт в памяти одного процесса и не разделяется между копиями сервера:

- код мастера первого запуска (`SETUP CODE`) меняется при каждом запуске службы;
- список внешних входов, которые сейчас проверяются (проверка «по одному на логин»);
- контроллер AD, который последним ответил;
- число одновременных проверок Kerberos и загрузок;
- состояние звонков по клику (окно звонка хранится около 10 минут; после перезапуска оно «не найдено»).

Счётчики неудач входа, сеансы, очередь и блокировки синхронизации хранятся в PostgreSQL и общие для всех копий.
