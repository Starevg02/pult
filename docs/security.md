# Безопасность Pult

Документ описывает модель безопасности Pult для администратора: что защищено и каким способом, что должен
сделать администратор при установке и эксплуатации, какие риски остаются. Устройство системы — в
[architecture.md](architecture.md), установка — в [install.md](install.md), доступ из интернета — в
[go-live.md](go-live.md). Описание относится к версии 0.1.0.

Pult держит пароли сотрудников только на время проверки, хранит служебные пароли в зашифрованном виде и
управляет доступом к ПК. Поэтому ошибка в настройке или в сети имеет последствия для всего домена. Чек-лист в
разделе 3 стоит пройти до первого пользователя.

## 1. Модель угроз

Pult рассчитан на следующие источники угроз:

- посторонний из интернета, если портал открыт наружу (подбор паролей, перехват трафика, эксплуатация ошибок);
- сотрудник с ограниченной ролью, который пытается получить чужие данные или больше прав;
- компрометация ПК сотрудника или ПК инженера;
- компрометация учётки домена (служебной, сотрудника, инженера);
- компрометация сервера Pult или его резервной копии;
- атакующий в локальной сети (между ПК, сервером, контроллерами домена, АТС, почтой).

Границы доверия:

| Граница | Как защищена |
|---|---|
| Браузер ↔ Pult | HTTPS, TLS 1.2 и 1.3, сессия в cookie, CSRF-токен |
| Pult ↔ контроллеры AD | LDAPS или StartTLS, проверка сертификата |
| Pult ↔ PostgreSQL | Пароль в переменной окружения или файле, рекомендуется локальное подключение или `scram-sha-256` |
| Pult ↔ агент и helper | Ключи и одноразовые токены, только исходящий HTTPS с ПК |
| Pult ↔ SMTP, вебхуки, АТС | SMTP — с TLS; вебхуки — `https` или `http` только на localhost; АТС — см. раздел 5 |

## 2. Что защищено и как

### 2.1. Транспорт

- Встроенный HTTPS: `rustls` с `ring`, TLS 1.2 и TLS 1.3, ALPN `h2` и `http/1.1`. TLS 1.0 и 1.1 не поддерживаются.
- `Strict-Transport-Security` (`max-age=31536000`) отдаётся, если HTTPS обслуживает сам Pult.
- Подключение к AD только по LDAPS или StartTLS. Схему `ldap://` в адресе контроллера указать нельзя. Отключить
  проверку сертификата контроллера нельзя: доверенные корни — системное хранилище и CA домена.
- Почта отправляется только по STARTTLS или TLS. Без шифрования отправка возможна лишь при `PULT_INSECURE_MAIL=1`,
  а эта переменная предназначена для разработки.
- Вебхуки: адрес `https` — на любой узел; `http` — только на `localhost`, `127.0.0.1` или `[::1]`. Адрес с логином
  и паролем не принимается. Переадресации не выполняются, ответ ограничен таймаутом 10 секунд.

### 2.2. Аутентификация

- Pult не хранит пароли сотрудников и не выдаёт им собственных паролей. Пароль проверяет контроллер домена
  (LDAP bind под учётной записью пользователя). Pult проверяет лишь то, что AD сообщил.
- Пустой пароль отклоняется до обращения к AD: анонимный bind иначе прошёл бы как успешный.
- Нет такой учётки и неверный пароль дают один и тот же ответ.
- Учётка ищется служебной учётной записью по экранированному фильтру (`ldap_escape`). Логин не попадает в фильтр
  без экранирования.
- Второй фактор — код из приложения (TOTP, RFC 6238). Он нужен при входе из-за пределов сетей организации тем, кто
  его подключил, и ролям из `totp_required_roles`. Код проверяется до обращения к AD. Один код принимается один раз
  (`totp_last_step`). Секрет хранится зашифрованным.
- Сквозного SSO нет: маршрут Kerberos только распознаёт пользователя по билету и не создаёт сеанс. Вход в портал
  выполняется паролем AD. Подробности — в [architecture.md](architecture.md), раздел 5.4.
- Токены API (`pult_…`) передаются заголовком `Authorization: Bearer`, хранятся хэшем и ограничены чтением.
  Их разрешения — пересечение выданных и тех, что есть у владельца.
- Токены регистрации агентов (`pae_`), ключи агентов (`pak_`) и одноразовые токены подключения (`pc_`) хранятся
  как SHA-256. Ключ агента показывается один раз. Токен подключения действует 60 секунд и принимается один раз.

### 2.3. Сеансы

- Токен сеанса — 32 случайных байта. В cookie он передаётся как `__Host-pult_session`: `HttpOnly`, `Secure`,
  `SameSite=Lax`, `Path=/`, без `Domain`. В базе лежит только SHA-256 от токена.
- Бездействие закрывает сеанс через 8 часов (настройка 1–72), абсолютный срок — 7 дней (настройка 1–30).
- Сеанс закрывается при выходе и при отключении учётки в AD. Если учётка отключена или пропала из AD, сеанс не
  действует даже до очистки: это проверяется в каждом запросе.
- При потере связи с доменом по умолчанию (`ad_outage_policy = block`) сеансы приостанавливаются после трёх
  неудачных проверок связи. Значение `grace` даёт ограниченное время работы без домена.
- Ответы API с данными (ФИО, телефоны, сеансы) отдаются с `Cache-Control: no-store`. Вложения тоже.

### 2.4. CSRF

Все изменяющие запросы проверяются в одном месте: в извлечении `CurrentUser`. Обработчик, который требует
пользователя, защищён сам. Токен CSRF хранится в строке сеанса и совпадает с заголовком `X-CSRF-Token`. Сравнение
идёт за постоянное время. Вход принимает только JSON, поэтому форма с чужого сайта на вход не отправится.

### 2.5. Права

- Каждый обработчик проверяет разрешение на сервере (`user.require(...)`). Интерфейс только прячет недоступное.
- Суперадминистратор имеет все разрешения. Роли и их разрешения хранятся в портале, а не берутся из групп AD.
- Выдать или снять разрешение можно только то, которое есть у самого администратора. Это защищает от
  самоповышения через управление ролями: при ошибке ответ `escalation`.
- Операция над собственной учёткой отклоняется, кроме запроса доступа, который согласовал владелец ресурса
  (решение принял другой человек).
- Публичные обработчики ограничены: вход, «Не могу войти» (только из заданных сетей и 3 обращения в час с адреса),
  ссылка «решено» из письма (одноразовая, с сроком).
- Неизвестный путь под `/api/` отвечает 404 в формате JSON, а не страницей интерфейса.

### 2.6. Журнал аудита

- Все значимые действия пишутся в `audit_log`: входы, выходы, изменения настроек, операции с AD, подключения к ПК,
  отказы по политике.
- Запись защищена хэш-цепочкой SHA-256. Триггеры запрещают `UPDATE`, `DELETE` и `TRUNCATE`. Цепочку проверяет
  задача `audit.verify` каждую ночь в 02:40; результат виден в админке.
- Журнал не очищается. В записи попадают «было/стало» и основание операций, но не пароли, токены и временные пароли.
- Журнал экспортируется в CSV. Ячейки, которые начинаются с `=`, `+`, `-`, `@`, таб или CR, экранируются, чтобы
  таблица не выполнила формулу.

Ограничение: тот, кто владеет таблицами (роль приложения или суперпользователь), может отключить триггеры и
переписать цепочку. Хэш-цепочка показывает подмену, только если последний хэш сохранён вне базы. Что делать — в
разделе 3.

### 2.7. Секреты

- Ключ шифрования: `PULT_SECRET_KEY` или файл `secret.key` в каталоге данных, создаётся при первом запуске с правами
  `0600`. Ключ короче 32 символов или с шаблонным значением `CHANGEME` не принимается.
- Из ключа выводится ключ AES-256-GCM (HKDF-SHA256). Зашифрованы: пароли служебных учёток чтения и записи, пароль
  SMTP, секреты вебхуков, секреты второго фактора, токен интеграции телефонии.
- Тип `Secret` не печатается в `Debug` и `Display`, не сериализуется и затирается в памяти.
- Ответы API не возвращают сохранённые пароли. Вместо значения сообщается признак «задан». Новый пароль принимается
  только в запросе.
- Смена адреса сервера (контроллеры, режим TLS, CA, почтовый сервер, адрес АТС) требует ввести пароль заново.
  Иначе сохранённый пароль ушёл бы на новый адрес.
- Пароли и ключи не попадают в журнал сервера. Проверка секретов в коде (ключи, пароли, незащищённый LDAP, отключённая
  проверка TLS, SQL через `format!`) выполняется хуком `.githooks/pre-commit`, который подключается командой из
  [CONTRIBUTING.md](../CONTRIBUTING.md).

### 2.8. Лимиты и блокировка

Лимиты по логину, по адресу и по суткам описаны в [architecture.md](architecture.md), раздел 4.8. Здесь важно
взаимодействие с AD.

- Портал считает неудачи по логину и по IP. Лимит по логину по умолчанию — 5 неудач за 5 минут. Домен блокирует учётку
  после своего порога. Поэтому портал должен закрывать вход раньше, чем домен заблокирует учётку. Иначе перебор
  через портал выведет сотрудника из строя.
- Когда портал отказывает по лимиту, он не обращается к AD. Счётчик домена при этом не растёт.
- Неверный пароль, полученный от одного контроллера, не повторяется на другом. Так попытка не удваивает счётчик
  блокировки в домене.
- Попытки из интернета считаются отдельно от попыток из сети организации. Перебор снаружи не закрывает вход
  сотрудникам в офисе.

### 2.9. Файлы

- Вложения принимаются только с расширением из белого списка. Для бинарных форматов проверяется сигнатура
  первых байт, текстовые проверяются на нулевые байты.
- Размер ограничен настройкой `max_file_mb` (по умолчанию 25 МБ, максимум 100). Одновременных загрузок — 8 на
  сервер и 2 на пользователя. Неприкреплённые файлы пользователя за сутки — не больше 50 файлов и 500 МБ.
- В браузере открываются только картинки PNG, JPEG, GIF и WebP. Остальное отдаётся как вложение (`attachment`).
  Пути формируются из SHA-256, имя файла при скачивании очищается.
- Скачать вложение заявки может тот, кто её видит: инженер, заявитель и наблюдатель. Внутренние вложения видят
  только инженеры. Неприкреплённый файл видит только тот, кто его загрузил. Для остальных ответ — `404`.
- Текст заявок и статей — Markdown. Сырой HTML не выводится: рендерер (`react-markdown`) не подключает обработку HTML.
  Ссылка подключения — только `pult://`. Шаблон ссылки «Написать письмо» — только `mailto:` или `http(s):`.

### 2.10. Заголовки и интерфейс

Каждый ответ сервера содержит:

- `Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`;
  в политике нет `unsafe-inline` и `unsafe-eval`;
- `X-Content-Type-Options: nosniff`;
- `Referrer-Policy: no-referrer`;
- `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`;
- `Cross-Origin-Opener-Policy: same-origin`.

Интерфейс не использует `innerHTML`, `dangerouslySetInnerHTML` и `eval`. Строки выводятся как текст. Токен сеанса
скрипту недоступен (`HttpOnly`). CSRF-значение читается из cookie только для заголовка.

### 2.11. Ограничения HTTP-запросов

- Время чтения заголовков — 10 секунд. Защита от медленных соединений (slowloris) работает, потому что таймер
  задан явно.
- Весь запрос с телом — 60 секунд. Загрузка больших файлов и пакетов агента — 600 секунд, но тело читается только
  после проверки входа и прав.
- Вход по Kerberos (`/api/auth/negotiate`) выполняет не больше 4 проверок одновременно.
- `/metrics` отдаётся только напрямую с `127.0.0.1` или `::1` без заголовков прокси, либо с токеном
  `PULT_METRICS_TOKEN` в заголовке `Authorization: Bearer`.
- `/health` отдаёт только состояние базы и версию.

### 2.12. Каталог AD: запись

- Только пять типизированных операций: добавить в группу, разблокировать, включить, отключить, сбросить пароль.
  Произвольного LDAP-изменения нет.
- Область задаётся списками OU и групп в настройках. Операция вне этих списков отклоняется. Право и область проверяются
  при запросе и снова при выполнении. Отозванное право или выведенный из области объект дают ошибку, AD не меняется.
- Учётка с `adminCount = 1` (защищённая AdminSDHolder) не меняется ни одной операцией.
- Сброс пароля выполняется только по LDAPS. Временный пароль — 16 символов из системного генератора, все четыре класса.
  Показывается запросившему один раз, неполученный удаляется через сутки.
- Каждая операция идемпотентна: повторная доставка задачи не выполняет её дважды. После записи результат читается
  заново.

### 2.13. Агент и удалённая поддержка

- Агент работает под LocalSystem, только с исходящими соединениями по HTTPS, сертификат портала проверяется по
  хранилищу Windows. Входящих портов агент не открывает.
- Регистрация: компьютер должен быть включённым компьютером AD, а адрес запроса — совпадать с его DNS-записью
  (`require_dns_match`, по умолчанию включено). Отключённый администратором компьютер не регистрируется сам.
- Обновление агента подписано Ed25519 закрытым ключом, который хранится у администратора офлайн. Подпись покрывает
  версию, платформу и SHA-256 файла. Агент принимает только более новую версию. Взлом сервера не даёт выполнить чужой
  код на ПК.
- Цель подключения — имя компьютера из AD и DNS-имя домена из настроек Pult. Имя из данных агента не используется.
  Helper отклоняет IP-адреса в качестве имени ПК и любые имена с символами вне имени хоста. Пути программ строятся
  от `%SystemRoot%`, аргументы передаются списком без командной оболочки.
- Ссылка `pult://connect` содержит одноразовый токен на 60 секунд. Адрес портала helper берёт из своей настройки,
  а не из ссылки. Итог подключения пишется в журнал и заметку заявки.
- Политика ПК: «Подключение запрещено» блокирует любое действие. «Только с согласием» запрещает действия без ведома
  пользователя (диск `C$`, управление компьютером, PowerShell). Подключение с управлением без запроса согласия
  требует права `remote.connect.control` и разрешено политикой.
- Каждое подключение и каждый отказ пишутся в журнал аудита.

### 2.14. Резервные копии

- Копия не содержит `secret.key`. Без ключа пароли служебных учёток из дампа не расшифровать.
- Каталог копий создаётся с правами `0700`. Копии хранятся 14 последних. Незавершённая копия не остаётся в списке.
- Пароль базы передаётся `pg_dump` переменной окружения, а не аргументом командной строки.

### 2.15. Служба и база

- Служба работает под отдельным пользователем `pult`, с `NoNewPrivileges`, `ProtectSystem=strict`, записью только в
  `/var/lib/pult`, фильтром системных вызовов, `MemoryDenyWriteExecute` и только `CAP_NET_BIND_SERVICE`
  (для порта 443). Файлы `/etc/pult/pult.env` и ключи — `root:pult 0640`.
- Роль базы `pult` не получает права суперпользователя. Пакет создаёт её и базу, расширения ставит администратор
  PostgreSQL.
- Миграции применяются одной транзакцией под блокировкой и не запускаются над базой от другой версии.

## 3. Что должен сделать администратор

Чек-лист. Пункты со ссылками подробно описаны в указанных документах.

### 3.1. При установке

- [ ] Установить сертификат портала: сертификат своего CA или публичный, не временный самоподписанный. Инструкция — в
      [install.md](install.md), раздел 6.
- [ ] Проверить, что `secret.key` сохранён отдельно от копий: на носителе в сейфе или в менеджере паролей. Без него
      служебные пароли не восстановить. См. [install.md](install.md), раздел 8.
- [ ] Создать служебную учётку чтения: обычный пользователь домена без административных групп, длинный пароль, срок
      без ограничения. Инструкция — [install.md](install.md), раздел 2.
- [ ] Если используется учётка записи, делегировать ей права только на OU обычных сотрудников и на группы доступа.
      Не давать права на OU с администраторами и служебными учётками, не входить в привилегированные группы.
      См. [directory.md](directory.md).
- [ ] Не использовать в домене учётку с правами администратора домена ни в качестве служебной, ни в качестве
      учётки записи.
- [ ] Назначить не меньше двух суперадминистраторов. Оба подключают код из приложения.

### 3.2. Сеть и прокси

- [ ] Если перед порталом стоит обратный прокси, задать `PULT_TRUSTED_PROXIES` с адресом прокси. Без этого все
      пользователи выглядят одним адресом, а вход из интернета нельзя отличить от входа из офиса.
- [ ] Не открывать PostgreSQL наружу. База — на localhost или во внутренней сети.
- [ ] Не открывать порт `8080` и другие служебные порты наружу. Наружу — только HTTPS портала.
- [ ] Настройки → Безопасность → «Сети организации»: перечислить свои сети точно, например `10.0.0.0/16`. Сеть шире
      `/8` портал не принимает. Настройку лучше не расширять, чтобы не получить лишних «внутренних» адресов.
- [ ] При установке через Docker проверить адрес клиента: на части систем Docker подменяет адрес клиента адресом своей
      сети (`172.x`). См. [go-live.md](go-live.md), абзац «Docker» в разделе 6.

### 3.3. Доступ из интернета

- [ ] Выполнить [go-live.md](go-live.md) полностью, включая проверку с телефона через мобильный интернет.
- [ ] Отметить в `totp_required_roles` инженеров и суперадминистраторов: через их учётки доступны все заявки,
      операции с AD и подключение к ПК. Настройка — Настройки → Безопасность.
- [ ] Выставить лимит неудач на логин строже порога блокировки домена. Например, если домен блокирует после 5 ошибок
      за 15 минут, поставить 4 неудачи за 15 минут.
- [ ] Проверить, что проброс порта на роутере не подменяет адрес источника (SNAT).

### 3.4. Роли и права

- [ ] Выдавать инженерам только нужные разрешения. Разрешения `directory.user.reset_password`,
      `directory.group.add_member`, `remote.connect.control` и `remote.manage` по умолчанию есть только у
      суперадминистраторов. Выдавать их инженерам осознанно.
- [ ] Не давать разрешения `core.roles.manage`, `core.settings.manage` и `directory.manage` никому, кроме
      суперадминистраторов.
- [ ] Выключить модули, которые организация не использует (настройка «Модули»). Выключенный модуль не отвечает
      на запросы.

### 3.5. Агенты и helper

- [ ] Не отключать проверку DNS при регистрации (`require_dns_match`). Отключение разрешает регистрацию под чужим
      именем компьютера, если у кого-то есть токен.
- [ ] Передавать токен регистрации предпочтительно свойствами MSI, а не групповой политикой. Ключ политики читают
      пользователи ПК, а с токеном пользователь может перерегистрировать свой ПК и подменять его сессии. Задать
      короткий срок токена и отозвать его после раскатки. См. [admin-guide.md](admin-guide.md), раздел 3.
- [ ] Закрытый ключ подписи обновлений агента хранить офлайн. Открытый ключ задать агентам при установке.
- [ ] Для теневого подключения GPO «Полный контроль с разрешения пользователя» — значение по умолчанию. Режим «без
      разрешения» включать только там, где тихое управление допустимо.
- [ ] Право теневого подключения давать отдельным админским учёткам инженеров, а не повседневным учёткам.

### 3.6. Телефония и почта

- [ ] Если используется АТС на Asterisk: учётка AMI с минимальными правами (запуск вызова и чтение состояния),
      `permit` только на адрес портала, сегмент сети закрыт от посторонних. Длинный случайный пароль.
- [ ] Почта: SMTP с TLS и проверкой сертификата. Учётку SMTP — только для отправки.

### 3.7. Сохранность и обновления

- [ ] Копии `/var/lib/pult/backups` забирать на другой сервер ежедневно. Копия содержит каталог `tls/` с закрытым
      ключом сертификата портала (см. раздел 5). Каталог и носитель с копиями защитить так же, как сам сервер.
- [ ] Метрики для внешней системы мониторинга — только с `PULT_METRICS_TOKEN`.
- [ ] Журнал службы писать в формате JSON (`PULT_LOG_FORMAT=json`, так задано пакетом) и собирать централизованно.
- [ ] Обновлять пакет по мере выхода версий. Перед обновлением читать `CHANGELOG.md`. Вернуться на прежнюю версию
      можно только до миграций. См. [install.md](install.md), раздел 9.
- [ ] Не копировать `.env`-файлы с секретами в репозитории и в переписку. Шаблон — `.env.example` с `CHANGEME`.
- [ ] После потери доступа к учётке или подозрения на компрометацию: сменить служебные пароли, отозвать токены
      регистрации и API, проверить журнал аудита и цепочку (`audit.verify`).

## 4. Доступ из интернета

Вход из интернета — отдельная задача с отдельными рисками. Порядок настройки, проверка и откат описаны в
[go-live.md](go-live.md). Кратко, что важно понимать:

- Снаружи вход работает, только если адрес клиента не из сетей организации. Этот адрес зависит от роутера и прокси.
- Снаружи второй фактор спрашивается у тех, кто его подключил, и у ролей из `totp_required_roles`. Остальные входят
  паролем AD, как в офисе. Это решение, которое принимает администратор, а не значение по умолчанию.
- Портал не может сам проверить, что роутер не подменяет адрес источника. Проверку делает администратор, см.
  [go-live.md](go-live.md), раздел 6.

## 5. Принятые риски и ограничения

Перечень того, что Pult не защищает или защищает не полностью. Учитывайте его при выборе способа установки.

| Риск или ограничение | Что это значит | Что делать |
|---|---|---|
| Владелец базы может переписать журнал | Триггеры можно отключить, цепочку пересчитать | Хранить последний хэш вне базы (выгрузка в syslog или почту администраторам — пока вручную) |
| Ответы AD раскрывают состояние учётки | Заблокированная, отключённая и истёкшая учётки различаются на входе, как в Windows | Учитывать при выборе, кому дать логин; это принятый компромисс |
| Перебор снаружи может закрыть вход сотруднику | Лимит по логину снаружи — 20 попыток в сутки; на сутки вход снаружи закрывается, в офисе работает | Держать лимит ниже порога блокировки домена |
| Перебор из интернета доходит до домена для учёток без кода | Попытки без второго фактора проходят до AD; домен может заблокировать учётку | Включить код для ролей с доступом к данным и операциям; держать лимит портала ниже порога домена |
| Исходный код открыт | Пороги лимитов видны всем, подбор упрощается для учёток без кода | Обязательный код для привилегированных ролей |
| Лимиты в памяти процесса | Проверка «один внешний вход на логин» и выбор контроллера не общие для копий сервера | Одна копия сервера на базу; при нескольких копиях учитывать это |
| Лимит считается по точному адресу | Клиент с большой подсетью IPv6 получает отдельный счётчик на каждый адрес. Общий лимит по логину сохраняется | Учитывать при выборе порогов; при необходимости ограничить подсеть на периметре |
| Секреты не привязаны к полю | Шифротекст одного поля можно записать в другое при записи в базу | Доступ к базе только у администратора; при смене формата привязку добавить |
| Ключ в копии не входит, каталог `tls/` входит | В копии есть закрытый ключ сертификата портала, без ключа шифрования | Защищать копии как сам сервер; при утечке копии сменить сертификат портала |
| Пакет при сбое после миграций не откатывается сам | Прежняя версия не стартует с обновлённой базой | Восстанавливать базу из копии ([install.md](install.md), раздел 8) |
| Вебхуки во внутреннюю сеть | `https`-адрес может быть внутренним узлом. Так задумано: чаты и системы внутри сети | Вебхуки создают только администраторы; проверять адреса |
| Телефония: AMI работает без TLS | Пароль не передаётся по сети (MD5-вызов), но перехват даёт материал для подбора | Длинный пароль, `permit` на портал, закрытая сеть |
| Телефония: звонить может любой вошедший сотрудник | Звонок на внутренний номер сотрудника из справочника доступен любому, у кого есть вход | Оценить, нужен ли модуль телефонии; при необходимости выключить |
| Токен регистрации в политике GPO | Его могут прочитать пользователи ПК и перерегистрировать свой ПК | Свойства MSI, короткий срок, отзыв после раскатки |
| Настройки helper в `HKCU` | Любой процесс пользователя может изменить адрес портала helper | Такой процесс уже действует от имени инженера; вне модели угроз helper |
| Итог подключения сообщает helper | Портал не может подтвердить, что пользователь принял запрос | Итог влияет только на журнал, не на решение о подключении |
| Открытый `/api/openapi.json` | Схема API доступна без входа | Схема не содержит данных, это осознанное решение |
| Мастер первого запуска | Код выводится в журнал службы. Пока суперадминистратора нет, тот, кто читает журнал, может завершить мастер | Завершить мастер сразу после установки |
| Зависимости с исключениями | В `deny.toml` перечислены исключения с обоснованием (`paste`, `pin-utils`, `rand` 0.7 через `tiberius`, только для Windows) | Проверять при обновлении зависимостей; CI выполняет `cargo deny` и `npm audit` |

## 6. Сообщить об уязвимости

Не создавайте публичный issue и не обсуждайте уязвимость в комментариях, pull request'ах и чатах. Сообщения
принимаются через приватный канал GitHub: вкладка **Security**, пункт **Report a vulnerability**. Публичного адреса
почты для отчётов пока нет. Порядок обработки, поддерживаемые версии и область действия — в
[SECURITY.md](../SECURITY.md).

В отчёте укажите версию Pult, способ установки, роль, с которой проверяется проблема, и шаги воспроизведения.
Перед отправкой удалите пароли, ключи, токены, адреса и данные сотрудников.
