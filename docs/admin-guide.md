# Руководство администратора: удалённая поддержка

Pult показывает, кто работает за каким ПК, и подключает инженера к сессии пользователя
штатным теневым подключением Windows (`mstsc /shadow`). Своего протокола удалённого доступа
у Pult нет: портал решает, **можно ли** подключиться и **как** (с согласием или без), а само
подключение идёт напрямую с ПК инженера на ПК пользователя средствами Windows.

```
ПК пользователя                Портал Pult                     ПК инженера
 служба PultAgent ──HTTPS──▶ /api/agent/v1/*   ◀──браузер──  карточка заявки
 (сессии, раз в минуту)      политики, аудит   ──pult://──▶  pult-helper.exe
          ▲                                     ◀──HTTPS───  (обмен токена, итог)
          └───────────── mstsc /shadow, SMB/RPC ──────────────────┘
```

## 1. Требования

### ПК пользователей

| Что | Зачем |
|---|---|
| Windows 10/11 или Windows Server 2016+, x64, в домене AD | Агент регистрируется, только если ПК есть в AD и включён |
| Служба PultAgent (MSI, раздел 3) | Отчёты о сессиях; запускается под LocalSystem |
| Исходящий HTTPS на портал (TCP 443) | Только исходящие соединения, входящих портов агент не открывает |
| Сертификат портала доверен Windows | Агент проверяет его по хранилищу Windows; внутренний УЦ раздаётся GPO |
| DNS-запись ПК совпадает с его адресом | Проверка при регистрации (можно отключить в настройках, не рекомендуется) |
| Политика теневых подключений (ниже) | Без неё Windows не разрешит `mstsc /shadow` |
| Брандмауэр: входящие SMB TCP 445 и правило «Удалённый рабочий стол — тень (TCP-In)» (`RdpSa.exe`, динамические порты RPC) с адресов инженеров | Теневое подключение. Порт 3389 и включённый RDP для тени **не нужны** |

Групповая политика теневых подключений:
`Конфигурация компьютера → Административные шаблоны → Компоненты Windows → Службы удалённых
рабочих столов → Узел сеансов удалённых рабочих столов → Подключения →
«Установить правила для удалённого управления сеансами пользователей служб удалённых рабочих столов»`.

- **«Полный контроль с разрешения пользователя»** — рекомендуемое значение по умолчанию.
  Windows всегда спрашивает пользователя, кнопка Pult «Без запроса» работать не будет.
- **«Полный контроль без разрешения пользователя»** — только для подразделений, где тихое
  управление допустимо (серверы, киоски). Pult и тогда спросит согласие при просмотре и на ПК
  из списка «Только с согласием».

Для быстрых действий из карточки ПК дополнительно нужны: «Диск C$» — общий ресурс `C$` (TCP 445);
«Управление компьютером» — правила брандмауэра «Удалённое управление службами», «Удалённое
управление журналом событий», WMI; PowerShell — WinRM (TCP 5985, `Enable-PSRemoting` через GPO).
«Проверка доступности» показывает ping, DNS и порты 3389/445/5985 с ПК инженера.

### ПК инженеров

- Windows 10/11, браузер с доступом к порталу.
- `pult-helper.exe` зарегистрирован для пользователя (раздел 4); прав администратора не нужно.
- Право на теневое подключение к ПК пользователей: группа инженеров в локальных
  администраторах ПК (GPO «Группы с ограниченным доступом» или предпочтение «Локальные
  пользователи и группы»), либо отдельное право тени для протокола RDP-Tcp:
  `wmic /namespace:\\root\CIMV2\TerminalServices PATH Win32_TSPermissionsSetting WHERE (TerminalName="RDP-Tcp") CALL AddAccount "EXAMPLE\pult-engineers",2`.

## 2. Права в Pult

| Разрешение | По умолчанию | Что даёт |
|---|---|---|
| `remote.device.view` | инженер, суперадмин | Раздел «Компьютеры», «где залогинен», сессии в карточке сотрудника |
| `remote.connect.view` | инженер, суперадмин | Подключение в режиме просмотра (всегда с запросом согласия), проверка доступности |
| `remote.connect.control` | суперадмин | Управление, «Без запроса», диск C$, управление компьютером, PowerShell (на ПК «Только с согласием» — только управление с запросом) |
| `remote.manage` | суперадмин | Настройки → Удалённая поддержка: токены, политики, пакеты, отключение ПК |

Роли меняются в «Настройки → Роли и права».

Удалённая поддержка — отдельный модуль: если она не нужна, выключите её в «Настройки → Система → Модули».
Раздел, кнопки подключения и API агента (`/api/agent`, отвечает «не найдено») пропадают, данные остаются;
агенты на ПК при этом не получают ответа и повторяют попытки, пока модуль не включат снова.

## 3. Установка агента

1. **Сборка.** MSI собирает CI (задание `windows`, артефакт `pult-windows`: `pult-agent.msi`,
   `pult-agent.exe`, `pult-helper.exe`). Загрузите MSI и helper в портал: «Настройки →
   Удалённая поддержка → Пакеты» (тип «MSI агента» / «Helper», версия, файл) и нажмите
   «Сделать текущим». Ссылки «Скачать MSI агента» и «Скачать helper» отдают текущие пакеты.
2. **Токен регистрации.** Там же, «Токены регистрации агентов» → название (например,
   «GPO: бухгалтерия») и срок (по умолчанию 30 дней). Токен показывается **один раз**.
   Токен многоразовый, но регистрирует только ПК, которые есть в AD и чей адрес совпадает с DNS.
   После раскатки токен можно отозвать: уже зарегистрированные агенты продолжат работать
   (у каждого свой ключ, на сервере хранится только его хэш).
3. **Параметры агента** — любым из способов (групповая политика важнее значений MSI):
   - свойства MSI:
     `msiexec /i pult-agent.msi /qn PORTALURL=https://pult.example.local/ ENROLLTOKEN=pae_… UPDATEKEY=…`
     → `HKLM\SOFTWARE\Pult\Agent` (ключ читают только SYSTEM и администраторы);
   - GPO «Предпочтения → Реестр» → `HKLM\SOFTWARE\Policies\Pult\Agent`, строковые значения
     `PortalUrl`, `EnrollToken`, `UpdatePublicKey`. Так удобно ставить MSI через «Установку
     программ» GPO, где свойства не передаются. **Ключ политик пользователи ПК могут читать**:
     с токеном пользователь может перерегистрировать свой ПК (не чужой — мешают проверки AD и DNS)
     и подменять его сессии. Поэтому предпочтительнее свойства MSI (через MST-преобразование для GPO),
     а токен — на короткий срок и с отзывом сразу после раскатки.
4. **Установка MSI** — GPO «Конфигурация компьютера → Политики → Конфигурация программ →
   Установка программ» (назначить) или вручную от администратора. MSI ставит
   `C:\Program Files\Pult\Agent\pult-agent.exe` и службу `PultAgent` (автозапуск, перезапуск при
   сбое). Обновление MSI без параметров сохраняет прежние значения.
5. **Проверка.** ПК появляется в разделе «Компьютеры» в течение минуты после запуска службы.
   Сессии обновляются раз в минуту и сразу при входе, выходе и блокировке.

Удаление: «Установка и удаление программ» или `msiexec /x pult-agent.msi /qn`. «Отключить» в списке
ПК с агентом отзывает ключ агента и запрещает повторную регистрацию этого ПК (например, если ПК
скомпрометирован или списан). «Включить» снимает запрет: агент зарегистрируется заново и получит
новый ключ, прежний не действует.

Проверка DNS при регистрации сверяет адрес, с которого пришёл запрос. Pult принимает HTTPS сам;
если поставить его за обратный прокси, адресом станет адрес прокси и регистрация не пройдёт.
Отключать проверку нельзя надолго: без неё любой с токеном регистрирует свой ПК под именем
чужого компьютера из AD.

## 4. Helper на ПК инженера

1. Скачайте helper из портала (ссылка в окне подключения или в настройках).
2. Выполните один раз из папки, куда скачали:
   `pult-helper.exe register --portal https://pult.example.local/`
   Helper копирует себя в `%LOCALAPPDATA%\Pult\pult-helper.exe` и регистрирует оттуда схему ссылок
   `pult:` и адрес портала — в `HKCU`, без прав администратора. Скачанный файл можно удалить.
3. При первом подключении браузер спросит, открыть ли Pult Helper — разрешите для портала.

Если инженер работает под обычной учётной записью, а права на ПК пользователей есть только у
его отдельной админской учётки, добавьте при регистрации `--prompt-credentials`: для теневого
подключения `mstsc` спросит учётные данные (`/prompt`), и тень пойдёт под админской учёткой.
Обычной учётке права администратора на ПК пользователей давать не нужно.

`--run-as ДОМЕН\adm-имя` (аналог NetOnly) делает то же для теневого подключения и, кроме того,
запускает «Управление компьютером» и PowerShell через `runas /netonly` под этой учёткой: пароль
спрашивает Windows в окне helper, helper его не видит и не хранит; учётные данные используются
только для обращений к удалённому ПК. Диск C$ открывается под текущей учёткой — Проводник не
запускается через `runas /netonly`; с файлами `\\ПК\C$` под админской учёткой работайте из окна
PowerShell, запущенного через Pult (`Copy-Item`, `Get-ChildItem`). Повторная регистрация без `--run-as` снимает настройку.

Адрес портала helper берёт только из своей настройки, а не из ссылки: чужая страница не может
направить его на другой сервер. Ссылка содержит одноразовый токен на 60 секунд; helper
обменивает его на параметры и сообщает порталу итог. Удалить: `pult-helper.exe unregister`.

## 5. Подключение

- **Из карточки заявки:** блок «Компьютер заявителя» → «Подключиться (просмотр, с согласием)».
  ПК берётся из поля «Компьютер» заявки, сессия — заявителя по данным агента. Новая заявка,
  созданная с ПК заявителя, получает имя этого ПК автоматически.
- **Из карточки ПК или «где залогинен»:** у каждой сессии — «Подключиться», «Управление»,
  «Без запроса»; «Ещё» — быстрые действия.
- Окно подключения показывает ход: «ждём helper» → «helper запущен» → «подключено» / ошибка.
  Успешное теневое подключение добавляет в заявку внутреннюю заметку.

Как портал решает: ПК в списке «Подключение запрещено» — отказ для любого действия (и запись
в аудит); просмотр — всегда с запросом согласия; управление без запроса — только с правом
`remote.connect.control` и если ПК не в списке «Только с согласием». На ПК «Только с согласием»
диск C$, управление компьютером и PowerShell запрещены (они дают доступ без ведома пользователя),
остаются теневое подключение с запросом и проверка доступности. Helper подключается к имени ПК из
AD в домене из настроек Pult — не к имени, которое сообщает агент.

Окно подключения и заметка в заявке показывают то, что сообщил helper инженера: что окно
подключения запущено и пользователю показан запрос. Принял ли пользователь запрос, Windows
порталу не сообщает.

## 6. Политики ПК

«Настройки → Удалённая поддержка → Политики ПК»: имя ПК, DNS-имя или шаблон со `*`
(`BUH-*`), правило «Подключение запрещено» или «Только с согласием». Импорт `policy.json`
прежнего инструмента переносит списки `ConsentRequiredComputers` и `DeniedComputers`;
строки, не похожие на имя ПК, показываются и пропускаются.

## 7. Обновление агента

Портал не может подписать обновление сам: ключ подписи хранится офлайн у администратора,
поэтому взлом портала не даёт запустить чужой код на всех ПК от имени SYSTEM.

1. Один раз, на ПК администратора: `pult-agent.exe keygen --out D:\offline\pult-update.key`.
   Закрытый ключ храните офлайн; открытый ключ (вывод команды) задайте агентам как
   `UPDATEKEY` / `UpdatePublicKey`. Без него агент обновления не принимает.
2. Для новой версии: `pult-agent.exe sign --key D:\offline\pult-update.key --version 1.0.0 pult-agent.exe`
   — выводит `sha256` и `signature`.
3. Загрузите `pult-agent.exe` как «Обновление агента» с этой версией и подписью и нажмите
   «Разослать агентам». Агент получит команду со следующим отчётом, проверит SHA-256 и подпись,
   заменит файл и перезапустится (служба поднимется сама). Агент ставит только версию **новее**
   своей; обновление с неверным хэшем, подписью или не новее установленного отклоняется и
   записывается в журнал. Подпись привязана к платформе (`windows-x86_64`) и версии.

## 8. Аудит

«Настройки → Аудит», действия `remote.*`: `remote.connect.requested`, `…opened`, `…started`,
`…failed`, `…denied`; `remote.device.enrolled`, `…deactivated`, `…activated`; `remote.token.created`,
`…revoked`; `remote.policy.created`, `…deleted`, `…imported`; `remote.package.uploaded`,
`…current`; `remote.settings.updated`. История подключений есть и в карточке ПК.

## 9. Диагностика

| Где | Что |
|---|---|
| `%ProgramData%\Pult\Agent\agent.log` | Журнал службы (до 5 МБ, затем `agent.log.old`) |
| `pult-agent.exe sessions` (от администратора) | Что агент отправит порталу: имя, ОС, адреса, сессии; ничего не меняет |
| `sc query PultAgent` | Состояние службы |
| Окно helper | Ошибка подключения и ответ портала; итог виден и в карточке ПК |

Частые причины: ПК нет в AD или он отключён (регистрация отклонена); адрес ПК не совпадает с DNS;
сертификат портала не доверен; брандмауэр закрывает 445/RPC; у инженера нет права тени на ПК;
GPO теней не задана («Без запроса» не работает при «с разрешения пользователя» — так и задумано).

## 10. Агент на Linux

Агент для Linux показывает в Pult рабочие станции и серверы на Linux: кто вошёл (локально, по SSH,
через XRDP), ОС, адреса и инвентаризацию (производитель, модель, BIOS, процессор, память, диски,
пакеты dpkg или rpm). **Подключения к сеансу у него нет**: теневое подключение — механизм Windows,
и портал отвечает «подключение к ПК на этой ОС не поддерживается». Обновления по сети агент на Linux
не получает — обновляйте его пакетным менеджером или заменой файла.

1. **Сборка** (на машине со сборочным окружением): `cargo build --release -p pult-agent` →
   `target/release/pult-agent`. Нужны systemd и `loginctl` на целевых машинах.
2. **Установка:**
   ```sh
   install -m 0755 pult-agent /usr/local/bin/pult-agent
   install -m 0600 deploy/linux-agent/pult-agent.conf.example /etc/pult-agent.conf
   install -m 0644 deploy/linux-agent/pult-agent.service /etc/systemd/system/pult-agent.service
   ```
   В `/etc/pult-agent.conf` укажите `PortalUrl` и `EnrollToken` (тот же токен регистрации, что
   для Windows, раздел 3). Машина должна быть в AD и в DNS — проверки при регистрации те же.
3. **Запуск:** `systemctl daemon-reload && systemctl enable --now pult-agent`. Ключ агента хранится
   в `/var/lib/pult-agent` (права 0700, файлы 0600); после регистрации токен из файла настроек можно
   удалить. Служба работает от root (нужно читать сеансы всех пользователей и DMI), но systemd
   закрывает ей запись в систему (`ProtectSystem=strict`) и повышение прав.
4. **Проверка:** `pult-agent sessions` — что агент отправит порталу; `pult-agent sessions --all` —
   то же с инвентаризацией. Журнал: `journalctl -u pult-agent`.

Удаление: `systemctl disable --now pult-agent`, удалить файлы выше и `/var/lib/pult-agent`;
в списке ПК — «Отключить».

## 11. Чего в удалённой поддержке нет

- **Собственного протокола** (подключение без RDP Shadow, к ПК вне домена и через NAT). Pult решает,
  можно ли подключиться, и пишет аудит, а картинку передаёт Windows. Свой протокол — это ретрансляция
  экрана и ввода через портал, отдельный транспорт и своя модель угроз; в 0.2.0 его нет. Для ПК вне
  домена используйте отдельный инструмент удалённого доступа, а заявку и итог фиксируйте в Pult.
- **Записи сеансов.** Теневое подключение идёт напрямую с ПК инженера на ПК пользователя, портал
  картинку не видит и записать её не может. Аудит фиксирует, кто, к какому ПК, когда и в каком режиме
  подключался (раздел 8).
- **Агента для macOS.** Есть агенты для Windows и Linux (раздел 10).
